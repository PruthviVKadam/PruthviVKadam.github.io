LLM / SQL · Safety · Live

Natural-language SQL that's safe by construction.

Schema-aware NL→SQL over DuckDB with a parse-time guardrail (single read-only SELECT) and a binder check that catches hallucinated columns before they run.

# the safety playground
DROP TABLE orders;        → BLOCKED (not read-only SELECT)
SELECT read_csv('/etc…')  → BLOCKED (denied function)
SELECT bogus_col FROM …   → FLAGGED (column doesn't exist)
SELECT name FROM orders   → ALLOWED (+ LIMIT 1000)

Problem

NL→SQL is high-value and easy to ship dangerously — it can mutate data, read files, or hallucinate columns a compliance team would never allow.

Approach

Generate SQL, then gate it: sqlglot parses to enforce a single read-only SELECT and deny file functions, inject a LIMIT, and a DuckDB binder (EXPLAIN) verifies every column exists.

Result

A copilot whose safety is measured against adversarial and hallucinated queries — not promised in a README.

Insights

What it shows

Parse, don't regex. An AST guard over sqlglot reasons about the query's structure — far harder to slip past than string matching on "DROP".

Hallucination is a binder problem. Asking DuckDB to EXPLAIN the query catches invented columns deterministically, before any rows move.

Measuring found the bugs. An adversarial suite caught read_csv slipping the guard and a false-flag on aliases — both fixed because they were tested, not assumed.
